# Нагрузочная проверка

## Запуск

```bash
make test-load

# Короткая проверка сценария, без вывода о производительности при 100 RPS:
LOAD_RATE=20 LOAD_SECONDS=5 LOAD_CONFLICT_SECONDS=2 make test-load
```

Нужен запущенный Docker с Compose. k6 2.3.0 закреплён по digest в
[docker-compose.load.yaml](../docker-compose.load.yaml). Сценарий работает
с новой БД в отдельном Compose-проекте и случайным HTTP-портом. Он не использует
рабочий Compose-проект. Контейнеры, сеть и volume удаляются также при ошибке.

Параметры: `LOAD_RATE` — запросы/с (1–2000), `LOAD_SECONDS` — длительность
смешанной нагрузки (1–600), `LOAD_CONFLICT_SECONDS` — длительность конфликтной
нагрузки (1–120). Произведение первых двух должно делиться на 10.
`DB_MAX_CONNS` задаёт размер пула API (по умолчанию 20).
Большие значения требуют больше времени на подготовку данных и ресурсов k6;
отказ подготовки или пропуски итераций считаются неуспешным прогоном.

Скрипт выводит путь к временной папке: `summary.json`, `k6.log`, `services.log`,
`environment.txt`, список образов и копии входных файлов. Папка сохраняется
после удаления окружения. JSON не содержит токены подготовленных пользователей.

## Методика

1. Через API создать 20 рабочих и 20 отдельных комнат для проверки гонок.
   В каждой рабочей комнате забронировать слот 09:00–09:30; подготовить
   достаточно уникальных свободных слотов на будущие даты в UTC.
2. Прогреть чтение слотов 5 секунд. Время подготовки и прогрева не входит
   в измерения смешанного профиля.
3. В течение 60 секунд отправлять 100 запросов/с. На каждые 10 запросов:
   5 чтений комнат, 2 чтения слотов, 1 чтение расписания, 1 новая бронь,
   1 совместимое изменение расписания. Обновления чередуют окончание дня
   18:00 и 19:00, сохраняя все забронированные слоты.
4. Отдельно 20 секунд отправлять 100 запросов/с в одну комнату: повторное
   бронирование занятого слота и изменение начала дня с 09:00 на 10:00.
   Требуются точные `409 SLOT_ALREADY_BOOKED` и `409 SCHEDULE_BOOKING_CONFLICT`.
5. В каждой из 20 отдельных комнат одновременно отправить 8 запросов на один
   свободный слот и 1 исключающее его изменение расписания. Допустимы только
   два исхода: одна бронь и отклонённое обновление либо успешное обновление
   и отклонение всех броней. Эти пакеты проверяют конкуренцию, а не целевые RPS.
6. Прочитать сохранённые данные: прежние брони сохранили ID и статус,
   новые брони существуют, активных дублей нет, итоговые расписания совместимы
   с бронями, результат каждой гонки сохранился в БД.

Используется [constant-arrival-rate](https://grafana.com/docs/k6/latest/using-k6/scenarios/executors/constant-arrival-rate/):
следующий запрос планируется независимо от длительности предыдущего.
Одна итерация смешанного и конфликтного профилей — один HTTP-запрос.
Между фазами есть 11 секунд на завершение запросов; timeout запроса — 10 секунд.

Порог успешности смешанного профиля — не менее 99,9% ожидаемых `2xx` с проверкой
содержимого ответа, как суммарно, так и по каждому виду запроса. После прогона
дополнительно требуется сохранение всех запланированных новых броней.
Ожидаемые `409` учитываются отдельно и не улучшают процент успешных `2xx`.
Для конфликтов и проверок целостности допустимых ошибок нет.

`request_ms` измеряет время вокруг HTTP-вызова на стороне k6, включая установку
соединения и получение тела, без последующей проверки JSON. Порог — **p95 < 200 мс**
суммарно и для каждого вида запроса. Это явная трактовка неоднозначного требования
«200 мс»; жёсткий максимум не гарантируется. Отдельно сохраняются p99 и max.

Требуются ноль `dropped_iterations` и полный запланированный объём запросов.
k6 может запустить ещё одну итерацию на самой границе интервала: допустим объём
от `rate × duration` до `rate × duration + 1`, недобор запрещён.
Поле `rate` у счётчиков в сыром JSON делится на время всего теста, включая другие
фазы и паузы. Частоту смешанного профиля следует считать по его объёму и 60 секундам.

Полный прогон завершён в 08:10:57 UTC. API соответствует `c044a87` (в этой
ревизии менялся только README); код API в рамках проверки не менялся.
SHA-256 сценария:
`ea7856b4c0a2359aeb508c4e787a90d77181fe6c24a854893fa5320f4e0e9ba5`.

Среда: Colima на macOS/ARM64, Linux VM с 2 CPU и примерно 1,91 GiB памяти,
Docker Engine 29.5.2, PostgreSQL 16-alpine, k6 2.3.0, пул API 20 соединений.
API, БД и генератор нагрузки работают в одной VM. БД новая; 40 комнат,
20 защищённых броней до нагрузки, 600 новых броней за смешанную фазу.
Тестовые JWT получены до нагрузки; регистрация и bcrypt-вход в профиль не входят.

6001 запрос за 60 секунд — около 100,02 RPS. Пропущенных итераций — 0.
Отдельный конфликтный профиль: 2001/2001 ожидаемых ответов.
Все 20 гонок и последующие проверки сохранённых данных прошли.

Первый короткий прогон завершился ошибкой только из-за первоначального
требования строго равного количества запросов: k6 отправил 101 вместо 100
и 41 вместо 40 на границах интервалов. Проверка исправлена на описанный выше
диапазон без разрешения недобора; все остальные проверки первого прогона прошли.

Ошибки API в этих сценариях не воспроизвелись. Замер подтверждает данный профиль
на небольшой новой БД. Он не подтверждает длительную доступность 99,9%, предел
пропускной способности, работу на большой истории броней, задержки внешней сети
или производительность другого окружения.

## Проверки самого сценария

```bash
# Node.js 22+; встроенный test runner, без npm-зависимостей.
make test-load-script
```

Тесты выполняют реальный код сценария с управляемыми ответами HTTP и проверяют,
что `null`, невалидный JSON, сломанная структура, `503`, неправильный `409`
и две успешные брони одного слота дают отрицательный результат.
Также проверяется отсутствие токенов в итоговом JSON. Эти проверки включены
в CI; полный нагрузочный прогон запускается отдельно от PR-проверок.
